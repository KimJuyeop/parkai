# 현장 시험 목록 (실제 카메라 · 장애 · 재부팅)

재생 시험(load_test)으로는 확인할 수 없는 것들이다. 실제 카메라에 붙인 보드에서 차례로 한다.
결과는 표의 '기록' 칸 값을 적어 두고, 기대와 다르면 그때의 상태와 로그를 남긴다.

## 준비

- 최신 번들 설치, 쓸 수 있으면 서버 전송·만공등도 켠다
- 상태 보기 (보드 PuTTY, 시험 내내 이걸로 본다):
  ```sh
  python3 -c "import json;s=json.load(open('/run/parkai/status.json'));print('start',s['started_at'],'cycle',s['cycle_sec'],'server',s['server_error']);[print(ip,c.get('status'),c.get('flicker'),c.get('smoothed','')) for ip,c in s['cameras'].items()]"
  systemctl is-active parkai-worker parkai-web
  journalctl -u parkai-worker -n 30 --no-pager
  ```
- `flicker`: 워커가 켜진 뒤 횟수. `blips` = 판정이 한 주기만 달랐다가 돌아온 횟수(연속 1회였다면 깜빡였을 횟수),
  `blips_empty`/`blips_occupied` = 그중 한 주기만 빈칸/차량 있음으로 나온 횟수,
  `changes` = 실제로 상태를 바꾼 횟수, `blip_slots` = 깜빡임이 있었던 칸별 횟수. 워커를 다시 켜면 0 부터
- `smoothed`: 잡음이 많아(밤) 평균해 줄인 렌즈 (밤 보정이 언제 켜지는지)

## 시험

| # | 시험 | 하는 법 | 기대 | 기록 |
| --- | --- | --- | --- | --- |
| 1 | 연속 동작 | 실제 카메라로 4시간 이상 그대로 둔다 (차가 드나드는 시간대 포함) | 사이클이 주기 안, 오류 없음 | 사이클 평균·최대, CPU, 온도, 카메라별 `flicker` |
| 2 | 카메라 한 대 끊기 | 카메라 랜선을 1~2분 뽑았다가 꽂는다 | 그 카메라만 '응답 없음', 그 칸은 마지막 상태 유지(서버·만공등 안 보냄). 다시 꽂으면 다음 주기부터 정상 | 끊긴 동안 사이클이 몇 초 늘었는지 (받기 제한 3초, 재시도 1회) |
| 3 | 서버 끄기 | 서버 프로그램을 멈추거나 서버 랜선을 뽑는다 | 모니터링 '서버 전송 오류', 판정·만공등은 계속. 서버가 돌아오면 다음 주기부터 전송 | 오류 표시·복구까지 걸린 시간 |
| 4 | 워커 강제 종료 | `systemctl kill -s KILL parkai-worker` | 3초 뒤 자동으로 다시 켜짐 (`active`). 모니터링이 잠깐 '정지'였다가 복구 | 복구까지 걸린 시간 |
| 5 | 보드 전원 재부팅 | 전원을 뽑았다 꽂는다 | 웹·워커 자동 시작, 설정 그대로. 최신 이미지는 첫 주기 뒤 다시 보임 (RAM 이라 비어 있음) | 전원~첫 판정까지 걸린 시간 |
| 6 | 카메라 재부팅 (만공등) | 만공등이 붙은 카메라만 재부팅 | 카메라가 돌아온 뒤 60초(`resend_sec`) 안에 만공등 색이 다시 켜짐 | 색이 돌아오기까지 걸린 시간 |
| 7 | 보드 랜선 끊기 | 보드 랜선을 1분 뽑았다가 꽂는다 | 그동안 모든 카메라 '응답 없음', 다시 꽂으면 자동 복구 | 복구까지 걸린 시간 |

## 1번 결과로 정할 것: 연속 확인 횟수 (차량 있음 / 빈칸)

칸 상태는 새 판정이 연속 N회 같아야 바뀐다. 기본 2/2 (5초 주기면 바뀐 상태가 5~10초 뒤에 보임).
시스템 설정 '판정' 에서 차량 있음(만차)·빈칸(공차) 쪽을 따로 바꾼다. 방향마다 따로 본다:

- `blips_empty` (차 있는 칸이 한 주기만 빈칸): 빈칸 확인 횟수를 정한다. 1회면 이만큼 차 있는 칸을 빈칸으로 안내했을 것
- `blips_occupied` (빈칸이 한 주기만 차): 차량 있음 확인 횟수를 정한다
- 거의 없으면(카메라당 하루 1~2회 이하) 그쪽을 1회로 줄여 5초 빨리 반영하고, 그보다 많으면 2회를 유지한다.
  2회로도 깜빡이면(`changes` 가 차가 드나든 횟수보다 훨씬 많음) 3회로 늘린다
- 특정 칸에 `blip_slots` 가 몰리면 횟수보다 그 칸 선분 위치를 먼저 본다 ([lines.md](lines.md))

## 알려진 한계

- 워커가 죽지 않고 멈추면(응답 없이 걸림) 지금은 자동으로 다시 켜지 않는다 (systemd 감시 미구현).
  모니터링에는 '정지'로 보인다. 시험 중 이런 일이 있으면 로그를 남긴다
