# 현장 시험 목록 (실제 카메라 · 장애 · 재부팅 · 설정)

재생 시험(load_test)으로는 확인할 수 없는 것들이다. 실제 카메라에 붙인 보드에서 차례로 한다.
현장에 보내기 전에 사무실에서 모두 통과시킨다 (아래 '현장 가기 전').
결과는 표의 '기록' 칸 값을 적어 두고, 기대와 다르면 그때의 상태와 로그를 남긴다.

## 준비

- 최신 번들 설치, 쓸 수 있으면 서버 전송·만공등도 켠다
- 상태 보기 (보드 PuTTY, 시험 내내 이걸로 본다):
  ```sh
  python3 -c "import json;s=json.load(open('/run/parkai/status.json'));print('start',s['started_at'],'cycle',s['cycle_sec'],'server',s['server_error']);[print(ip,c.get('status'),c.get('flicker'),c.get('smoothed','')) for ip,c in s['cameras'].items()]"
  systemctl is-active parkai-worker parkai-web
  journalctl -u parkai-worker -n 30 --no-pager
  ```
- `flicker`: 워커가 켜진 뒤 횟수. `blips` = 판정이 한 주기만 달랐다가 돌아온 횟수(연속 1회였다면 깜빡였을 횟수),
  `blips_empty`/`blips_occupied` = 그중 한 주기만 빈칸/차량 있음으로 나온 횟수,
  `changes` = 실제로 상태를 바꾼 횟수, `blip_slots` = 깜빡임이 있었던 칸별 횟수. 워커를 다시 켜면 0 부터
- `smoothed`: 잡음이 많아(밤) 평균해 줄인 렌즈 (밤 보정이 언제 켜지는지)

## 시험

| # | 시험 | 하는 법 | 기대 | 기록 |
| --- | --- | --- | --- | --- |
| 1 | 연속 동작 | 실제 카메라로 4시간 이상 그대로 둔다 (차가 드나드는 시간대 포함) | 사이클이 주기 안, 오류 없음 | 사이클 평균·최대, CPU, 온도, 카메라별 `flicker` |
| 2 | 카메라 한 대 끊기 | 카메라 랜선을 1~2분 뽑았다가 꽂는다 | 그 카메라만 '응답 없음', 그 칸은 마지막 상태 유지(서버·만공등 안 보냄). 다시 꽂으면 다음 주기부터 정상 | 끊긴 동안 사이클이 몇 초 늘었는지. 예상: 처음 한 주기 약 6초, 그 뒤 약 3초 늘어남 (렌즈 2개여도) |
| 3 | 서버 끄기 | 서버 프로그램을 멈추거나 서버 랜선을 뽑는다 | 모니터링 '서버 전송 오류', 판정·만공등은 계속. 서버가 돌아오면 다음 주기부터 전송 | 오류 표시·복구까지 걸린 시간 |
| 4 | 워커 강제 종료 | `systemctl kill -s KILL parkai-worker` | 3초 뒤 자동으로 다시 켜짐 (`active`). 모니터링이 잠깐 '정지'였다가 복구 | 복구까지 걸린 시간 |
| 5 | 보드 전원 재부팅 | 전원을 뽑았다 꽂는다 | 웹·워커 자동 시작, 설정 그대로. 최신 이미지는 첫 주기 뒤 다시 보임 (RAM 이라 비어 있음) | 전원~첫 판정까지 걸린 시간 |
| 6 | 카메라 재부팅 (만공등) | 만공등이 붙은 카메라만 재부팅 | 카메라가 돌아온 뒤 60초(`resend_sec`) 안에 만공등 색이 다시 켜짐 | 색이 돌아오기까지 걸린 시간 |
| 7 | 보드 랜선 끊기 | 보드 랜선을 1분 뽑았다가 꽂는다 | 그동안 모든 카메라 '응답 없음', 다시 꽂으면 자동 복구 | 복구까지 걸린 시간, 끊긴 동안 사이클 (20대 예상: 처음 약 18초, 그 뒤 약 9초) |

| 8 | 시계 (인터넷 없음) | 보드 랜선을 뽑은 채 전원을 뽑았다 꽂고 `date`, `timedatectl` | 시계가 틀려도 모니터링은 '동작 중'이고 '몇 초 전'도 맞게 보임 (보드 시계끼리 비교) | 재부팅 뒤 보드 시각과 실제 시각 차이, RTC 유무 |
| 9 | 서버 전송 내용 | 보드에서 `python3 /opt/parkai/current/tools/fake_server.py` 를 띄우고 웹 '서버 전송' 주소를 `http://127.0.0.1:9000` | 주기마다 카메라별 `ps01~ps12` 가 한 줄씩 찍힘 (1 차량 있음, 0 빈칸, unknown 칸 없음). `--fail` 로 띄우면 3번과 같음 | 칸 번호·값이 화면과 같은지 |
| 10 | 만공등 색 | 칸을 비우고 채우며 본다 (차를 빼거나 선분을 빈 곳으로 옮겨 저장) | 빈칸 종류 색, 여러 종류면 1순위 색, 다 차면 빨강. 순위를 바꿔 저장하면 바로 바뀜 | 색이 바뀌기까지 걸린 시간 |
| 11 | 설정 바로 반영 | 웹에서 인식 기준, 확인 횟수, 주기, 만공등 색·순위, 기록 이미지, 칸·선분을 바꿔 저장 | 워커를 다시 켜지 않아도 다음 주기부터 반영 (`journalctl` 에 '설정 반영') | 반영 안 되는 항목 |
| 12 | 화면에 없는 설정 | 시스템 설정 '설정 파일' 내보내기 → 메모장으로 값 하나 고침(예: `fetch_timeout_sec`) → 가져오기 | 가져오기 뒤 그 값으로 동작. 잘못된 값은 거부되고 기존 설정 유지 | |
| 13 | 인터넷 없는 노트북 | 노트북 와이파이를 끄고 보드와 같은 망에서 웹 화면 | 글꼴·화면이 깨지지 않음, 모든 메뉴 동작 | |
| 14 | 선분 그리기 리허설 | 칸이 많은 카메라에 '선 추가'로 연속해서 긋고 저장 ([lines.md](lines.md) 기준) | 판정이 실제와 맞음 | 칸 12개 긋는 데 걸린 시간 |
| 15 | 원격 업데이트·되돌리기 리허설 | 아래 '원격 업데이트' 순서대로 새 번들 설치 → 되돌리기 명령 | 시스템 설정 첫 줄의 빌드 이름이 바뀌고, 되돌리면 이전 빌드로 돌아감. 설정은 그대로 | 걸린 시간 |

## 현장 가기 전 (사무실)

현장은 인터넷이 없다. 원격 데스크톱으로 현장 PC에 접속해 새 번들은 올려 설치할 수 있지만(번들은 인터넷 없이 설치됨),
보드에 시스템 패키지(apt: X-LINUX-AI, OpenCV 등)를 새로 깔 수는 없다. 위 1~15 를 사무실에서 먼저 모두 통과시킨다.

- 순서: 5, 8(전원·시계) → 9, 3(서버) → 10, 6(만공등) → 11, 12, 13, 14(설정·화면) → 15(업데이트) → 2, 4, 7(장애) → 1(하룻밤)
- 1번은 하룻밤 이상 그대로 두고 `flicker`·10분 요약으로 확인한다 (`journalctl -u parkai-worker | grep 최근`)
- 현장 설정을 사무실에서 미리 만들어 둔다: 카메라 목록(IP·카메라 프로필·렌즈 수), 카메라 계정, 서버 주소,
  보드 이름. '설정 파일 내보내기(비밀번호 포함)' 로 저장해 가면 현장에서는 가져오기와 선분 긋기만 하면 된다

## 현장에 가져갈 것

- 설치 번들(`parkai-<버전>-stm32mp25.tar.gz`), 모델 폴더 `yolov2t_hf`(예비 `st_full_pc`)
- 노트북: PuTTY, 웹 브라우저, 미리 만든 현장 설정 파일, 이 목록
- 현장 정보: 카메라 IP·기종·계정·스냅샷 주소, 서버 주소, 보드에 줄 IP

## 원격 업데이트 (현장 PC 경유)

1. 사무실: 새 번들 `parkai-<버전>-stm32mp25.tar.gz` 준비. 빌드 이름(`버전-날짜-커밋`)은 번들을 만들 때 찍힌다
2. 크롬 원격 데스크톱의 파일 전송으로 현장 PC에 올린다
3. 현장 PC 명령 창에서 보드로 복사: `scp parkai-0.1.0-stm32mp25.tar.gz root@<보드 IP>:/tmp/`
   (윈도우 10 이상은 `scp`·`ssh` 가 기본으로 있다. 없으면 WinSCP·PuTTY 설치 파일도 같이 올린다)
4. 현장 PC에서 `ssh root@<보드 IP>` 로 접속해 설치:
   `cd /tmp && rm -rf parkai-0.1.0-stm32mp25 && tar xzf parkai-0.1.0-stm32mp25.tar.gz && cd parkai-0.1.0-stm32mp25 && ./install.sh`
5. 확인: 현장 PC 브라우저로 보드 웹 → 시스템 설정 첫 줄의 빌드 이름, 모니터링 '동작 중'
6. 문제가 있으면 되돌리기 (설치 끝에 나오는 명령과 같음):
   `ln -sfn $(readlink /opt/parkai/previous) /opt/parkai/current && systemctl restart parkai-worker parkai-web`

- 빌드마다 `/opt/parkai/<빌드 이름>` 에 따로 설치되고 최근 3개까지 남는다. 설정·모델·기록 이미지는 `/var/lib/parkai` 라 그대로
- 현장 PC가 보드와 같은 망인지(웹 접속, `ssh`)는 현장 가기 전에 확인한다
- 새 번들이 보드에 없는 시스템 패키지를 요구하면 현장에서 설치할 수 없다. 의존성은 지금 것(시스템 OpenCV·numpy·stai_mpu + 번들 wheel)으로 고정한다

## 현장에서 모아 올 것

- 하룻밤 사진 (밤 성능·기준값 확인용). 보드가 카메라와 같은 망이라 보드에서 바로 모은다.
  PuTTY 를 닫아도 계속 돌도록 `nohup` 으로 띄운다 (20대×렌즈 2개, 10분 간격, 14시간이면 SD에 약 340MB):
  ```sh
  nohup python3 /opt/parkai/current/tools/collect_snapshots.py --ip <카메라 IP 여러 개> --password <비밀번호> \
      --lenses 2 --out /var/lib/parkai/collect --interval 600 --hours 14 > /tmp/collect.log 2>&1 &
  ```
  IDIS 가 아닌 카메라는 `--url` 로 스냅샷 주소를 준다. 다 모으면 노트북으로 옮기고 보드에서는 지운다
- 1번 결과: 카메라별 `flicker`, 10분 요약, 기록 이미지(`/var/lib/parkai/results`)
- 카메라 기종별 판정용 스트림 해상도, 밤 모드(컬러/흑백 적외선) 메모
- 보드의 `find` 는 간이 버전(BusyBox)이라 `-printf` 같은 옵션이 없다

## 1번 결과로 정할 것: 연속 확인 횟수 (차량 있음 / 빈칸)

칸 상태는 새 판정이 연속 N회 같아야 바뀐다. 기본 2/2 (5초 주기면 바뀐 상태가 5~10초 뒤에 보임).
시스템 설정 '판정' 에서 차량 있음(만차)·빈칸(공차) 쪽을 따로 바꾼다. 방향마다 따로 본다:

- `blips_empty` (차 있는 칸이 한 주기만 빈칸): 빈칸 확인 횟수를 정한다. 1회면 이만큼 차 있는 칸을 빈칸으로 안내했을 것
- `blips_occupied` (빈칸이 한 주기만 차): 차량 있음 확인 횟수를 정한다
- 거의 없으면(카메라당 하루 1~2회 이하) 그쪽을 1회로 줄여 5초 빨리 반영하고, 그보다 많으면 2회를 유지한다.
  2회로도 깜빡이면(`changes` 가 차가 드나든 횟수보다 훨씬 많음) 3회로 늘린다
- 특정 칸에 `blip_slots` 가 몰리면 횟수보다 그 칸 선분 위치를 먼저 본다 ([lines.md](lines.md))

## 알려진 한계

- 워커가 죽지 않고 멈추면(응답 없이 걸림) 지금은 자동으로 다시 켜지 않는다 (systemd 감시 미구현).
  모니터링에는 '정지'로 보인다. 시험 중 이런 일이 있으면 로그를 남긴다
